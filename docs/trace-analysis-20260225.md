## 3. 문제 ①: 30초 빈 화면

### 현상

데이터가 t=1.8초에 준비되었으나, 실제 렌더링은 t=33.8초에야 시작된다. 그 사이 30초간 loop()가 매 프레임 **0.066ms**만에 리턴하고 있다.

### 원인 추정

loop() 내부에 뷰포트/extent 정보 검사가 있고, Worker가 초기 뷰포트 메시지를 수신하지 못하여 매 프레임 early return하는 것으로 보인다. 사용자가 팬/줌 조작을 해야 뷰포트 메시지가 전달되어 그때서야 렌더링이 시작된다.

### 해결 방향

Worker 초기화 완료 후, 메인 스레드에서 현재 뷰포트 정보를 **즉시 전송**하도록 수정한다. 또는 Worker가 데이터 로드 완료 시 메인에게 `ready` 메시지를 보내고, 메인이 그때 뷰포트를 전달하는 핸드셰이크를 구현한다.

```
Worker: loadData 완료 → postMessage({ type: 'ready' })
Main:   onmessage('ready') → postMessage({ type: 'viewport', extent, zoom, size })
```

## 4. 문제 ②: WASM 계산이 프레임의 97.7%

### 렌더링 트레이스 핵심 수치

렌더링 중 측정한 3.3초 트레이스에서 Worker loop()의 프레임 분석:

| 지표 | 값 |
|------|-----|
| 총 프레임 | 16개 |
| 평균 프레임 시간 | **185ms** |
| 최소 / 최대 | 149ms / 256ms |
| WASM 계산 비율 | **97.7%** (3,034ms 중 2,964ms) |
| 대기/기타 | 2.3% (71ms) |

프레임 간격이 거의 정확히 `dur + 5ms`이며, setTimeout 대기가 거의 없이 연속으로 계산하고 있다. Worker CPU 사용률이 97.7%로 완전 포화 상태다.

|-----------|------|------------|----------|

## 5. 문제 ③: 줌 아웃 시 성능 저하

### 정량 비교

전체 트레이스에서 줌 상태 변화에 따른 프레임 시간:

| 구간 | 추정 줌 상태 | avg(ms) | FPS | 프레임 수 |
|------|------------|---------|-----|----------|
| 35-37s | 줌아웃 (넓은 뷰) | 41.9 | ~24 | 41 |
| 37-39s | 줌아웃 | 49.3 | ~20 | 36 |
| 39-41s | 줌아웃 | 52.7 | ~19 | 34 |
| 41-43s | 줌아웃 | 52.9 | ~19 | 36 |
| 43-45s | 줌아웃 (최대) | 63.4 | ~16 | 31 |
| 45-47s | **줌인 전환** | 26.3 | ~38 | 54 |
| 47-49s | 줌인 | 28.1 | ~36 | 60 |

**줌아웃/줌인 비율: 1.9배** (avg 기준 51.4ms vs 27.2ms)

렌더링 전용 트레이스(줌아웃 상태 고정)에서는 **185ms/frame = 5.3 FPS**.

### 원인 분석

줌아웃 시 느려지는 것은 **뷰포트 범위와 무관하게 전체 파티클을 처리**하고 있기 때문이다.

현재 구조에서 매 프레임 수행하는 작업:

```
loop() 1프레임 내부:
  1. 전체 파티클(N개) 순회
     └ 각 파티클마다:
       ├ R-tree로 현재 위치의 삼각형 탐색 → O(log 580,000)
       ├ Barycentric 보간으로 UV 계산
       └ 위치 이동 + 수명 관리
  2. 전체 파티클을 Uint8Array로 직렬화
  3. postMessage로 메인 스레드 전송
```

파티클 수를 3,500개로 가정하면, 185ms / 3,500 = **파티클당 0.053ms**. 이 중 R-tree 탐색(580,000 삼각형에서 log N)이 가장 비용이 클 것으로 추정된다.

줌아웃 시 추가 비용이 발생하는 원인:
- 뷰포트 밖 파티클도 동일하게 계산 (뷰포트 컬링 없음)
- 또는 줌아웃 시 파티클 수가 동적으로 증가하는 로직이 있을 수 있음

## 6. 문제 ④: 첫 프레임 1,283ms 스파이크

t=33.8초의 첫 실제 프레임이 1,283ms 소요된다. 이는 30초간 빈 루프를 돌다가 처음으로 뷰포트 정보가 설정되면서 **전체 파티클 초기 스폰 + 첫 계산**이 한번에 실행되기 때문이다.

해결: 문제 ①(초기 뷰포트 전달)이 해결되면, 데이터 로드 직후(t=1.8s) 첫 프레임이 실행되므로 사용자 체감상 빈 화면 시간이 크게 줄어든다. 첫 프레임 자체의 1.3초 비용은 파티클을 점진적으로 스폰하는 방식으로 완화할 수 있다.

## 8. 개선 방향

### 8.1 즉시 적용 (코드 수정)

**① 초기 뷰포트 전달 (문제 ①)**

Worker `ready` → Main이 현재 뷰포트 전송. 30초 빈 화면 해소.

**② 뷰포트 컬링 (문제 ②③)**

뷰포트 밖 파티클은 업데이트를 건너뛰고, 뷰포트 밖으로 나간 파티클은 뷰포트 안에서 리스폰한다. 줌아웃 시에도 "화면에 보이는 파티클"만 계산하면 된다.

예상 효과: 줌인 시와 동일한 28ms 수준으로 수렴.

### 8.2 WASM 내부 최적화 (Rust 코드 확인 필요)

**③ wasm-function[134] 프로파일링**

이 함수의 정체를 확인해야 한다. Rust 소스에서 `wasm-pack build` 시 `--profiling` 플래그로 빌드하면 함수명이 트레이스에 노출된다.

```bash
wasm-pack build --profiling --target web
```

또는 `wasm-opt --print-functions` 로 인덱스 → 함수명 매핑을 확인할 수 있다.

추정되는 후보:
- `getUpdateParticles()` 내부의 파티클 순회 루프
- `interpolate_uv()` (보간 계산)
- R-tree `locate_all_at_point()` (삼각형 탐색)

**④ R-tree 탐색 최적화 — 인접 삼각형 워킹**

현재: 매 프레임, 파티클마다 R-tree 전체 탐색 O(log N)
개선: 이전 프레임의 삼각형 인덱스를 기억 → 인접 삼각형만 확인 O(1)

파티클은 매 프레임 조금만 이동하므로, 대부분 같은 삼각형에 있거나 인접 삼각형으로 이동했을 것이다. 삼각형 연결 정보(adjacency)를 저장하면 R-tree 없이 O(1) 탐색이 가능하다.

**⑤ 직렬화 비용 절감**

wasm-function[94]가 직렬화라면 (18.6%), 전체 파티클을 매 프레임 Uint8Array로 패킹하는 대신 SharedArrayBuffer 또는 ptr+len 직접 접근으로 복사를 제거할 수 있다. 단, 이전 논의에서 API 변경 최소화를 위해 보류한 항목이다.

### 8.3 파티클 수 동적 조절

줌 레벨에 따라 파티클 수를 조절한다. 줌아웃 시 넓은 영역을 커버하려면 더 많은 파티클이 필요하지만, 성능 한계 안에서 밀도를 타협해야 한다.

| 줌 레벨 | 파티클 수 | 예상 프레임 시간 | FPS |
|---------|----------|---------------|-----|
| 넓은 뷰 | 2,000 | ~106ms | ~9 |
| 중간 | 3,500 | ~185ms | ~5 |
| 좁은 뷰 | 1,500 | ~79ms | ~13 |

현재 구조에서 파티클 수를 줄이는 것만으로는 30fps 달성이 어렵다. **내부 알고리즘 최적화(④)가 병행**되어야 한다.

### 8.4 프레임 레이트 목표 역산

30fps(33ms) 달성을 위해 허용되는 파티클당 비용:

| 목표 FPS | 프레임 예산 | 파티클 3,500개 시 파티클당 | 파티클 2,000개 시 파티클당 |
|----------|-----------|------------------------|------------------------|
| 30 | 33ms | 0.0094ms | 0.0165ms |
| 20 | 50ms | 0.0143ms | 0.025ms |
| 15 | 67ms | 0.019ms | 0.033ms |

현재 파티클당 0.053ms → 목표 0.017ms (3배 개선 필요).

R-tree O(log N) → 인접 워킹 O(1) 전환으로 삼각형 탐색 비용을 10배 이상 줄일 수 있으며, 이것만으로 3배 개선이 가능할 것으로 예상된다.
